Stage 1 of 7. Data Preprocessing & Extraction (phase1_preprocessing)
You are here: Stage 1 of 7
Workflow: Stage 1 (Preprocessing) → Stage 2 (JSON→Markdown) → Stage 3 (Taxonomy) → Stage 4 (NER) → Stage 5 (Dedup) → Stage 6 (Graph) → Stage 7 (Vector)
What happens
Progressively refine raw PDFs into structured JSON using a 3-stage extraction process.
3-Stage Extraction Process (within Stage 1)
Stage 1 runs the complete preprocessing pipeline which internally contains:
Internal Stage 1: PDF OCR with Docling + PyMuPDF (structural parsing to extract hyperlinks)


Internal Stage 2: LLM agenda extraction with regex fallbacks


Internal Stage 3: Ontology enhancement with entity extraction


Discovery and prioritization
Scan for new or modified PDFs with checksums and timestamps


Prioritize partially processed files


Skip logic commonly avoids reprocessing all already processed files 
Digitization and caching
OCR converts documents to machine-readable text and layout


OCR output is cached


Extraction to JSON
Extract text and layout, including OCR when needed


Build structured JSON with agenda items, sections, and metadata


Deterministic filename linking
Files like MM_DD_YYYY - Verbatim Transcripts - <agenda-codes>.pdf link transcripts to agenda items without LLM


This is completely deterministic


Stage 1 outputs - the data contract
Document-level metadata from Internal Stage 1 (OCR):
doc_id: Unique document identifier (e.g., "DOC_abc123def456")


source_file_name: Original filename


source_file_path: Full path to source file


full_text: Extracted text content


pages: [] (array, pages extraction)


hyperlinks: Array with {url, text, page, coordinates}


metadata:


extraction_method: "docling_ocr_pymupdf" or "skipped_already_processed"


page_count: Number of pages from PDF


total_chars: Character count of full_text


hyperlink_count: Number of hyperlinks found


extraction_timestamp: ISO timestamp


provenance: Records extraction tools (Docling, PyMuPDF) and whether fallbacks were taken


Additional metadata added in subsequent internal stages:
Document_Type: Normalized to enum (Agenda | Verbatim | Ordinance | Other) - added during classification


processing_status: Tracks pipeline progress


checksum: For change detection


discovery_time and processed_time: Timestamps for tracking


Internal Stage 2 within Stage 1: Agenda Structure Extraction
This happens inside the Stage 1 pipeline for agenda files:
Extracted metadata:
meeting_date: Extracted from document content


sections: Array of {section_name, section_id, start_line, end_line}


agenda_items: Array with:


item_code: (e.g., "E-1", "F-10")


document_reference: (e.g., "23-6784")


title: Item title text


section_name: Parent section


Locale-aware date normalization:
 Ambiguous inputs such as 01.09.2024 standardized to ISO YYYY-MM-DD using document locale rules while keeping the raw string
This data is passed to Internal Stage 3 (within Stage 1) for ontology enhancement.
Internal Stage 3 within Stage 1: Ontology Enhancement
This stage enhances the agenda structure and saves enhanced JSON files:
Output: Enhanced JSON files saved to organized subdirectories:
agenda/ - Enhanced agenda files


legal/ - Enhanced ordinances and resolutions


verbatim/ - Processed transcript files


Upstream quality gates and validation
Gate A: Structural fidelity. All top-level headings present. Tables round-trip to Markdown grids. Anchors are unique


Gate B: Metadata completeness. Required fields present such as doc_id, source_file_name, source_file_path, full_text


Gate C: JSON structure integrity. Valid JSON with expected schema


Gate D: Ontology enhancement. Enhanced JSON files prepared for downstream processing


Gate E: Provenance and traceability. doc_id consistent. Extraction metadata complete


Why Stage 1 matters
Structured JSON enables precise taxonomy extraction


Metadata normalization ensures consistency


Traceability from provenance and source tracking


Sets foundation for all downstream processing

Stage 3 of 7. Taxonomy Synthesis (phase2_building)

You are here: Stage 3 of 7
Workflow: Stage 1 (Preprocessing) → Stage 2 (JSON→Markdown) → Stage 3 (Taxonomy) → Stage 4 (NER) → Stage 5 (Dedup) → Stage 6 (Graph) → Stage 7 (Vector)
What happens
Parse structured JSON from Stage 1 to create typed entities with deterministic IDs
 Store in simple_ner_graph/registry/ directory (same structure as NER will use)
Note: This is different from the ontology enhancement in Stage 1 (Internal Stage 3). Stage 3 creates the authoritative taxonomy entities that will be used as the skeleton of the graph.
How Stage 3 differs from Stage 1’s internal step
Stage 1, internal step 3: Enhances the agenda structure and saves organized JSON files.


Stage 3: Creates the authoritative entities with deterministic IDs, standardized metadata, and complete provenance tracking.


Stage 3 entity example:
{
  "personID": "person_john_smith",
  "firstName": "John",
  "lastName": "Smith",
  "title": "Commissioner", 
  "type": "Person",
  "Meeting_Date": "2024-01-09",
  "source_file_name": "agenda_01_09_2024.json",
  "_sources": "taxonomy_agenda"
}

Inputs
Agenda JSON produces Meeting, Section, AgendaItem entities


Legal documents produce Policy entities such as Ordinance or Resolution with official numbers and titles


Verbatim transcripts produce Document nodes linked to the right agenda items via deterministic filename pattern


LLM integration with guardrails and fallbacks
Extract sections, item codes such as E-1, document references such as 23-6819, complete legal titles without truncation, sponsors, motions, and vote summaries


Regex and rule-based fallbacks provide minimum viable structure if LLM calls fail


Deterministic, date-aware IDs
agenda_item_<item_code>_<MM_DD_YYYY> such as agenda_item_e1_01_09_2024. Normalized date form also supported internally for joins. This means the system supports multiple date formats for the same agenda item to enable proper matching and deduplication


Internal joins support agenda_item_<item_code>_<MM_DD_YYYY>


Example: agenda_item_e4_2024_01_09 and agenda_item_e4_2024_02_13 are different meetings with the same code


policy_<type>_<year>_<number> such as policy_ordinance_2024_01


policy_ordinance_2024_01_[hash8] to avoid collisions


person_{firstName}_{lastName} such as person_john_smith. NEVER include titles in person IDs to avoid ID instability when roles change. Use collision suffixes for duplicate names: person_john_smith_2


Metadata added by Stage 3
For each entity created:
Meeting_Date: From agenda extraction (ISO format)


Document_Type: Classification (Agenda, Ordinance, Resolution, etc.)


committeeOrBody: Extracted from agenda header


policyNumber: For Policy entities


source_file_name/path: Inherited from Stage 1


_sources: "taxonomy_agenda" or similar to track origin


Output location
Entities written to simple_ner_graph/registry/{EntityType}/ directories


Relationships written to simple_ner_graph/registry/relationships/

Stage 4 of 7. NER Extraction (phase2_building)
You are here: Stage 4 of 7
Workflow: Stage 1 (Preprocessing) → Stage 2 (JSON→Markdown) → Stage 3 (Taxonomy) → Stage 4 (NER) → Stage 5 (Dedup) → Stage 6 (Graph) → Stage 7 (Vector)
What happens
Process Markdown from Stage 2 using Phase 1 entities as context


Each Markdown chunk is processed by four parallel LLM calls, one per entity group:


Group 1: People and Roles (Person, Role, Organization)


Group 2: Governance and Actions (Meeting [stored as Event], Event, Action, VoteOutcome, Board)


Group 3: Documents and Policies (Document, AgendaDocument, Policy, Contract, LegalReference, Section)


Group 4: Content and Resources (AgendaItem, Presentation, PublicComment, Project, Location, Asset, Technology, Topic, Appointment)


Single-pass triple extraction yields typed entities with standardized IDs and relationships with attributes and full provenance


Chunking strategy
Markdown is chunked into about 1,500 characters with about 10 percent overlap


Character limit (or token limit) to prevent JSON parsing failures from oversized LLM responses


Sentence-aware chunking that doesn't split tables, list items, or legal titles


Chunks saved to simple_ner_graph/document_chunks/ directory as .txt files


Chunking and processing approach
Uses Phase 1 entities for logging purposes (about 50-100 entities typically logged)


Processes markdown chunks independently using 4 parallel ontology groups


Chunk filenames: Named using the format {chunk_id}.txt where chunk_id is a unique identifier (often a hash-based ID like chunk_abc123def456.txt), with each file containing a metadata header followed by the chunk content separated by a --- delimiter. The chunk files have this structure:
# Chunk ID: chunk_abc123def456
# Document: agenda_01_09_2024.json
# Document Type: agenda
# Meeting Date: 01.09.2024
# Index: ⅓
# Source: city_clerk_documents/extracted_json/agenda/agenda_01_09_2024.json
—
[Actual chunk text content here]



LLM guardrails and fallbacks
Ontology-aligned emission ensures required ID fields and attributes are present and aligned


Reading-status classification (such as ordinances first versus second reading) uses LLM classification with deterministic fallbacks based on section headers and formulaic phrases


Rule-based fallback keeps a baseline when an LLM call fails


API rate limiting is handled at runtime with configurable delays between calls (not stored as metadata)


Pre-flight token counting prevents exceeding context limits


Regex and rule-based fallbacks provide minimum viable structure if LLM calls fail


Metadata added by Stage 4
Each extracted entity includes:
extraction_chunk_id: Which chunk it came from (for debugging).


_sources: "ner_chunk_X" to track NER origin. The _sources field is particularly important because it determines merge priority during deduplication - entities with taxonomy_ sources get priority over ner_ sources when merging duplicates.


Confidence scores (internally used, not stored)


Example Stage 4 (NER) entity:
{
  "personID": "person_john_smith",
  "firstName": "John",
  "lastName": "Smith",
  "title": "Commissioner",
  "type": "Person", 
  "votePosition": "yes",
  "extraction_chunk_id": "chunk_transcript_01_09_2024_005",
  "_sources": "ner_chunk_5",
  "source_file_name": "01_09_2024_verbatim_transcript.txt"
}

What Stage 4 adds vs Stage 3:
Stage 3: Basic taxonomy entity with ID and metadata


Stage 4: Four parallel ontology-focused LLM calls per chunk, each specialized for domain expertise
Per-chunk entity extraction with no awareness of other chunks or documents
Attribute enrichment beyond basic taxonomy using contextual analysis
Implicit relationship discovery within chunk boundaries (organizational membership inferred from titles, procedural relationships from discussion context)


Output location
Entities written to simple_ner_graph/entities/{EntityType}/ directories


Relationships written to simple_ner_graph/relationships/


Indices built in simple_ner_graph/indices/


Why this stage exists
Captures entities and relationships found only in body text or transcripts outside agenda header structure


Uses Phase 1 entities as context for consistency



Stage 5 of 7. Multi-Source Deduplication (phase2_building)
You are here: Stage 5 of 7
Workflow: Stage 1 (Preprocessing) → Stage 2 (JSON→Markdown) → Stage 3 (Taxonomy) → Stage 4 (NER) → Stage 5 (Dedup) → Stage 6 (Graph) → Stage 7 (Vector)
Goal
Unify Taxonomy's authoritative entities (from Stage 3) with NER's broad entities (from Stage 4) into a single canonical set
EntityDeduplicatorExtended
Name normalization: Strip titles, standardize casing. Harmonize attribute names such as meetingDate versus meeting_date


Similarity scoring that is configurable:


60 percent name similarity


30 percent attribute overlap


10 percent contextual similarity


Two-stage thresholds:


Candidate generation around 0.85 to collect plausible matches


Final merge at 0.95 or higher to avoid over-merging legal records (configurable via ENTITY_SIMILARITY_THRESHOLD env var)


Merge priority: taxonomy over ner. Taxonomy remains authoritative. NER fills missing attributes and links


Missing endpoints: Auto-create minimal stubs for referenced but unseen nodes that can be enriched later


Incremental support: Version tracking, conservative merges that preserve existing values, list-property union, and conflict logs


Relationship rewiring: Updates relationship endpoints to point to canonical entity IDs, tracking rewired edges, unresolved references, and duplicate relationship removal


Opportunity for attribute enrichment through intelligent merging (not yet implemented): Rather than simply discarding duplicate entities, the system enriches canonical entities (from both taxonomy and NER sources) by selectively incorporating valuable attributes from duplicate candidates when confidence thresholds are met, creating more complete entity profiles while maintaining source-based priority rules
Outputs
Merged Entity Manifests at simple_ner_graph/merged/entities/{Type}.json


Relationship Manifest at simple_ner_graph/merged/relationships.json


Merge Map at simple_ner_graph/merged/merge_map.json mapping old_id → canonical_id

Stage 6 of 7. Graph Construction (phase2_building)
You are here: Stage 6 of 7
Workflow: Stage 1 (Preprocessing) → Stage 2 (JSON→Markdown) → Stage 3 (Taxonomy) → Stage 4 (NER) → Stage 5 (Dedup) → Stage 6 (Graph) → Stage 7 (Vector)
Validation before write
Schema validation: Required fields present and correctly typed


Relationship validation: Enforce ontology constraints such as Section hasAgendaItem → AgendaItem. Reject invalid patterns such as Person → Section


Sanity checks: No orphans. Unique IDs. Referential integrity


Graph build with CustomGraphBuilder to Cosmos DB Gremlin
Batch writes about 500 items per batch, parallel execution, connection pooling, retry with exponential backoff, automatic reconnection on transient failures


On validation failure: log and continue so processing does not halt


Provenance everywhere: Each node and edge carries source_file_name|path, _sources such as taxonomy_agenda or ner_chunk_5, extraction_chunk_id, and tool or version


Packaging and downstream
Structured entities and relationships to Cosmos DB Gremlin


All validation logs and statistics tracked for observability

Layer 4. Detailed reference
Foundations first: data model, ontology, taxonomy, metadata, identifiers
Ontology and taxonomy
Ontology is the system's blueprint. Defines core nouns, verbs, adjectives


Entities (Nouns): Person, Organization, Document, Policy, Event, Action, Asset, Project, Location, Role, Topic, AgendaItem, Section, Meeting, AgendaDocument, Contract, LegalReference, VoteOutcome, Board, Technology, Presentation, PublicComment, Appointment

Attributes (Properties): Descriptive facts such as item_code for AgendaItem or firstName/lastName for Person (name computed as alias)


Relationships (Verbs): Connections such as a Person can SPONSOR an AgendaItem


Taxonomy is a hierarchical structure derived directly from documents. Example: a Meeting contains Sections that contain AgendaItems. Provides the authoritative backbone for the Taxonomy Graph


Data model and ontology, concise but actionable
Purpose: Provide a typed model that the graph can enforce and extraction can populate consistently


Core entity classes (actual scope from UnifiedOntology):


People & Organizations: Person (canonical: firstName, lastName; name as computed field), Organization, Role


Documents & Legal: Document, AgendaDocument, Policy, Contract, LegalReference


Meetings & Structure: Meeting (stored as Event), Section, AgendaItem, Board


Actions & Outcomes: Event, Action, VoteOutcome


Resources & Context: Asset, Project, Location, Technology, Topic


Participation: Presentation, PublicComment, Appointment


Attributes: Typed key-value facts on entities and edges such as ordinance numbers, agenda codes, titles, dates, outcomes

Person attributes: firstName and lastName are canonical fields for query matching; name field computed as alias for display

Attributes contribute 30 percent to dedup scoring


Relationships (edges): Typed predicates constrained by the ontology


Examples that are valid:


Section hasAgendaItem → AgendaItem


AgendaItem implements → Policy


Edges carry attributes such as vote details and provenance


The rules (ontology) define classes, predicates, and allowed source → predicate → target patterns


Used for extraction focus, validation, and graph build


Taxonomy maps structured JSON to ontology classes, provides deterministic IDs and high-precision attributes. When merging, Taxonomy wins over NER

Appendix. Recap: Stage Framing Aligned to Implementation
Preserves the original descriptions expanded with comprehensive implementation details and actual stage numbering.
Stage 1: Data Preprocessing & Extraction (The Raw Material)
Entry point where raw PDFs are fully processed through a sophisticated 3-stage internal pipeline.
Discovery and prioritization: Scan for new or modified PDFs with checksums and timestamps, prioritize partially processed files, skip logic avoids reprocessing of routine runs


Runs complete preprocessing pipeline which internally contains:


Internal Stage 1: PDF OCR extraction with Docling + PyMuPDF for structural parsing and hyperlink extraction


Internal Stage 2: LLM agenda extraction with comprehensive regex fallbacks, extracting sections, item codes, complete legal titles, sponsors, motions, and vote summaries


Internal Stage 3: Ontology enhancement with LLM entity extraction from agenda items, creating Person, Organization, Document, AgendaItem, Meeting, and Policy entities (currently unused by downstream NER)


Quality gates: Structural fidelity, metadata completeness, JSON integrity, ontology enhancement, provenance traceability


Outputs: Structured JSON to organized subdirectories (agenda/, legal/, verbatim/) with comprehensive metadata including doc_id, source file tracking, meeting dates, extraction timestamps, and provenance


Stage 2: JSON to Markdown Conversion (Format Bridge)
Converts structured JSON to LLM-processable Markdown while preserving document integrity.
Format transformation: Converts structured JSON from Stage 1 into clean Markdown format


Structure preservation: Maintains document hierarchy, headings, lists, and metadata linkage


Processing enablement: Creates text format required for Stage 4 NER chunk-based processing


One-to-one mapping: Maintains direct correspondence between source JSON and output Markdown files


Stage 3: Taxonomy Synthesis (The Skeleton)
Sophisticated entity synthesis from structured JSON creating the authoritative knowledge graph backbone.
Comprehensive entity creation: Processes agenda, legal, and verbatim JSON files to create Event, Document, Section, AgendaItem, Person, and Policy entities


Deterministic ID generation: Creates collision-resistant, date-aware IDs with formats like agenda_item_e1_2024_01_09 and policy_ordinance_2024_01


Hierarchical relationship building: Establishes complex relationship chains (Event → hasAgenda → Document → hasSection → Section → hasAgendaItem → AgendaItem)


Cross-validation: Policy number validation against filenames, URL extraction from hyperlinks, sponsorship relationship creation from motion details


Registry structure: Writes to simple_ner_graph/registry/ using the same directory structure that NER will populate


Stage 4: NER Extraction (The Flesh)
Per-chunk text analysis extracting entities and relationships from narrative content.
Chunk-based processing: Analyzes individual 1,500-character chunks independently with no cross-chunk awareness


Four parallel LLM calls per chunk using focused ontology views:


People & Roles: Person, Role, Organization entities


Governance & Actions: Meeting, Event, Action, VoteOutcome, Board entities


Documents & Policies: Document, AgendaDocument, Policy, Contract, LegalReference, Section entities


Content & Resources: AgendaItem, Presentation, PublicComment, Project, Location, Asset, Technology, Topic, Appointment entities


Triple-based extraction: Subject-predicate-object relationships with full attribute extraction and provenance tracking


Narrative intelligence: Captures implicit entities, contextual attributes, and relationships found only in discussion text and transcripts


Output scope: Entities written to simple_ner_graph/entities/{EntityType}/, relationships to simple_ner_graph/relationships/, indices to simple_ner_graph/indices/


Stage 5: Multi-Source Deduplication (Unifying the Data)
Sophisticated entity and relationship consolidation with intelligent attribute enrichment.
Multi-source similarity scoring: Configurable weighted algorithm using 60 percent name similarity, 30 percent attribute overlap, 10 percent contextual similarity


Two-stage thresholds: Candidate generation around 0.85 to collect plausible matches, final merge at 0.95 or higher to avoid over-merging legal records


Intelligent merge priority: Taxonomy over NER with selective attribute enrichment from duplicate candidates when confidence thresholds are met


Relationship rewiring: Updates all relationship endpoints to point to canonical entity IDs, tracking rewired edges, unresolved references, and duplicate relationship removal


Missing endpoint handling: Auto-creates minimal stubs for referenced but unseen nodes that can be enriched later. These are tagged accordingly. 


Incremental processing: Version tracking, conservative merges preserving existing values, list-property union, comprehensive conflict logging


Output manifests: Merged entities, relationships, and complete merge map with old_id → canonical_id mappings, similarity scores, and merge reasoning


Stage 6: Graph Construction (Final Assembly)
Validated graph database construction with comprehensive quality assurance.
Pre-flight validation: Schema validation for required fields, relationship validation against ontology constraints, referential integrity checks, orphan detection


Batch optimization: Writes validated entities and relationships to Cosmos DB Gremlin in 500-item batches with parallel execution, connection pooling, exponential backoff retry, and automatic reconnection


Provenance preservation: Every node and edge carries complete metadata including source_file_name|path, _sources tracking (taxonomy_agenda, ner_chunk_X), extraction_chunk_id, tool versions


Error resilience: Validation failures logged and skipped to prevent pipeline halt, comprehensive statistics tracking for observability


Stage 7: Vector DB Push (Search Enablement)
Semantic search infrastructure with canonical entity alignment.
Chunk indexing: Pushes document chunks from simple_ner_graph/document_chunks/ to Azure Cognitive Search with rich metadata


Canonical ID mapping: Uses merged entity mappings to resolve all entity references in chunks to canonical IDs, ensuring consistency between graph and vector systems


Embedding generation: Creates semantic embeddings for chunk text with metadata for filtering and faceting


Cross-modal consistency: Enables seamless queries across both graph database (precise relationships) and vector index (semantic search) using unified entity identifiers


Pipeline Philosophy:
Sequential refinement from raw PDFs → structured JSON → comprehensive taxonomy skeleton → narrative flesh → unified canonical graph → searchable vector index, with each stage building precision and coverage while maintaining complete provenance and traceability.



Phase 3. Querying (phase3_querying)

 Classify →  Retrieve → Synthesize. An LLM classifies intent, selects a retrieval plan across a graph architecture plus a vector index, then synthesizes a structured answer with citations and a confidence score.
Router
 Four mutually exclusive query types that are collectively exhaustive:
SPECIFIC_FACT → graph lookup in Cosmos DB via Gremlin


GENERAL_INFO → vector search with embeddings


COMPLEX_HYBRID → multi hop hybrid with both graphs and vector


UNCLEAR → disambiguation dialogue, then re route


Hybrid rule of thumb
 Graph for precise facts and relationships. Vector for contextual meaning and narrative. Fuse the two, reconcile conflicts, rank, cite, and calibrate confidence.
Output format
 Executive summary, detailed bullets, inline citations [G#] for graph and [V#] for vector, confidence score.

2.2 Inputs, Transformations, Outputs
Inputs (query time)
User Query: text plus optional constraints (date ranges, document types, jurisdictions)


Knowledge Stores: Taxonomy Graph in Cosmos DB Gremlin, NER Graph, Vector Index of markdown chunks


Schemas and Taxonomy: UnifiedOntology for classes, attributes, constraints; Topic taxonomy with hierarchy and synonyms


Metadata: document level, chunk level, graph level, vector level as produced by the pipeline


Config and Policies: hop limits (≤2 graph plus ≤2 vector), thresholds, ranking weights, QueryValidator rules


Caches: graph property and path cache, vector top k cache, embeddings cache


Transformations
 Normalization → Classification → Routing → Dynamic Gremlin generation → Semantic expansion → Retrieval → Multi hop orchestration → Fusion → Ranking and confidence calibration → Answer synthesis.
Query Normalization: Clean user input, extract entities, standardize date formats


Intent Classification: LLM determines query type (SPECIFIC_FACT, GENERAL_INFO, COMPLEX_HYBRID, UNCLEAR)


Routing Decision: Route to graph-only, vector-only, or hybrid retrieval based on classification


Dynamic Query Generation:


Graph path: Generate Gremlin queries using LLM with ontology constraints


Vector path: Create embeddings and execute KNN search with semantic similarity


Multi-Hop Orchestration: For complex queries, execute up to 4 hops with gap analysis between each hop


Result Fusion: Combine graph and vector results, resolve conflicts (graph priority), deduplicate by source


Ranking and Scoring: Apply weighted formula (40% graph relevance + 30% vector similarity + 20% temporal + 10% authority)


Confidence Calibration: Calculate final confidence (base 0.5 + boosts for multiple sources, citations, specificity)


Answer Synthesis: LLM generates natural language response with structured format and inline citations

Outputs
 Human readable answer with executive summary and structured bullets. Inline [G#] and [V#] provenance. Confidence score. Optional disambiguation options and machine artifacts for traceability.

Layer 4. Querying Rules
4.1 Query type playbooks
SPECIFIC_FACT
 When: single identifiable lookup with clear IDs.
 Retrieval path: generate constrained Gremlin from UnifiedOntology, execute in Cosmos DB, collect fact with provenance.
 Output: direct fact with [G#].


GENERAL_INFO
 When: broad thematic request without specific IDs.
 Retrieval path: embed query, vector kNN over chunks with taxonomy expansion, return top k snippets, synthesize.
 Output: summary with [V#].


COMPLEX_HYBRID
 When: needs both relationships and narrative across entities.
 Retrieval path: up to 4 hops total (≤2 vector + ≤2 graph) driven by gaps. H1 Vector to find candidates → H2 Graph to connect entities → H3 Vector to fill context → H4 Graph to verify identities and counts.
 Output: fused answer with [G#] and [V#].


UNCLEAR
 When: ambiguous terms or missing constraints.
 Retrieval path: detect ambiguity, fetch candidate entities, show numbered options, on selection re enter router.
 Output: disambiguation list, then standard answer.


4.2 Fusion, ranking, confidence
Fusion: de duplicate entities, merge complementary facts, resolve conflicts with Graph facts preferred for canonical data, preserve all citations.


Ranking formula: score = 0.4*graph_relevance + 0.3*vector_similarity + 0.2*temporal_proximity + 0.1*entity_authority.


Confidence: start 0.5, add for dual path corroboration and high similarity, subtract for ambiguity or missing graph corroboration, cap at 1.0.


4.3 Simple router heuristics
If identifiers are present → Graph first.


If exploratory wording dominates → Vector first.


If relationship phrasing appears → Hybrid.


Adaptive rule: start narrow, widen scope only when gaps remain.


4.4 Guardrails
Generate Gremlin only within UnifiedOntology constraints.


Normalize dates to ISO and retain originals. No invented dates.


Normalize Cosmos results and resolve aliases.


Deduplicate by source and canonical IDs.


Use fallback layers in order: Graph plus Vector → local NER indices -> keyword.
